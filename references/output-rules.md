# 无障碍输出规则的设计依据

## 为什么不做「大字版网页」

市面上已有无障碍点餐方案采用 Web + ARIA 标签的路径。本项目不重复这条路，
因为对视障用户而言，**读屏软件读的是文本流，不是视觉大小**。

一个零依赖的命令行程序，输出直接进管道、直接被 NVDA / VoiceOver 朗读，
不需要浏览器、不需要装 Node、不需要视觉渲染。这是本质差异，不是功能重叠。

## screen-reader 模式七条规则

| 规则 | 反例（读屏实际念出的） | 正例 |
|---|---|---|
| 金额念中文货币 | 「19.88 元」→ 「十九点八八元」 | 「十九元八角八分」 |
| 单位全中文 | 「311 mg」→ 「三一一 M G」 | 「311 毫克」 |
| 禁用符号 | 「★ 推荐」→ 「星号 推荐」 | 「推荐」 |
| 禁用表格 | 表格会念「第 2 行第 3 列」 | 「第三项」 |
| 禁用缩写 | 「SKU」→ 念字母 | 展开写 |
| 显式进度 | 直接念 8 条，听者不知道还有多久 | 先报「共 8 项」再逐条 |
| 编号连写 | 「第 一 项」 | 「第一项」 |

## 实测中发现并修正的三个真实缺陷

这些不是理论推演，是跑真实数据后暴露出来的：

### 1. 纯按钠升序会把可乐顶到第一位

钠 = 0 的饮品在「钠最低」排序里永远第一，但对「这一餐吃什么」毫无帮助。

**修法**：两条启发式规则（名称命中饮品/甜品关键词，或能量低于阈值）
把餐食与甜品饮品分开，只对餐食做主餐建议。

### 2. 序号跳号

早期实现用「达标项上限」作为第二段列表的起始序号，当达标项不足时会出现
「第一、二、三、四、六项」，读屏用户会以为漏念了一项。

**修法**：改用显示序号连续递增。

### 3. 组合建议会超出额度

早期只对**单项**做额度校验，导致推荐「脆薯饼 311 mg + 麦乐鸡 422 mg = 733 mg」，
而本餐额度是 666.7 mg —— 每项都合格、加起来超过参考值。

**修法**：组合选择加入合计约束，`total + val > limit` 即跳过；
任一成分数据缺失就不敢加总，宁可不推荐。
对限钠人群来说，这种「看起来都合格」的建议比不推荐更危险。

## large-print 模式

服务老年用户与认知障碍者：一次只给 3 个选项，条目之间留空行。
不是把字号调大，而是**减少同时呈现的信息量**。

## 门店排序的可达性含义

`rank_stores` 按「营业中优先 + 距离升序」。对行动不便者，
**少走 500 米**是真实的收益。但必须同时说明：
MCP 不返回坡道、无障碍卫生间、低位柜台等数据，本工具无法核实，请致电门店确认。
